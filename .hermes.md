# Tent of Trials Hermes Context

Tent of Trials is a trading and risk platform assembled from several
language stacks. Treat it like a production system that survived because
people were careful, not because the architecture is elegant.

## Project Purpose

- Provide market data, order handling, matching, analytics, and compliance
  experiments in one repository.
- Keep each module independently buildable.
- Favor small, reversible changes. The repo already has enough dramatic
  history; do not add a new chapter unless the issue asks for it.

## Tech Stack by Directory

- `backend/`: Rust service code. Start with `Cargo.toml`, then `src/`.
- `frontend/`: TypeScript and React UI code. Start with `package.json`.
- `market/`: Go market gateway, order book, matching, analytics, AI, and
  compliance code. Start with `market/main.go`.
- `frailbox/`: C components. Start with the top-level `Makefile`.
- `frailbox/engine/`: C++ engine code built through CMake.
- `frailbox/nfc/`: Lua scanner code. Start with `scanner.lua`.
- `compliance/`: Java compliance auditor. Start with
  `ComplianceAuditor.java`.
- `v2/services/`: Ruby market stream service. Start with
  `market_stream.rb`.
- `v2/scripts/`: Operational scripts. Read `log_watchdog.pl` first for the
  house style and its hard-earned paranoia.
- `docs/openapi/`: Haskell OpenAPI tooling. Start with `Types.hs`, then
  `Validate.hs`, `Generate.hs`, and `Server.hs`.
- `tools/`: Lua OpenAPI tools and the `encryptly` diagnostic helper.
- `diagnostic/`: Required build diagnostic artifacts.

## Common Development Commands

Run commands from the repository root unless noted otherwise.

```sh
python3 build.py
python3 build.py --clean
python3 build.py --module market
python3 build.py --module backend,frontend
python3 build.py --release
```

Module-specific checks from `build.py`:

```sh
(cd backend && cargo build)
(cd frontend && npm run build)
(cd market && go build -o market .)
(cd frailbox && make)
(cd frailbox/engine && cmake --build build)
(cd compliance && javac -d build ComplianceAuditor.java)
(cd v2/services && ruby -c market_stream.rb)
(cd frailbox/nfc && luac -p scanner.lua)
(cd docs/openapi && ghc -fno-code Types.hs Server.hs Validate.hs Generate.hs)
(cd tools && luac -p openapi_diff.lua openapi_mock.lua openapi_pact.lua)
```

## Build and Diagnostic Workflow

Always run this after changes:

```sh
python3 build.py
```

Include the generated diagnostic artifact in pull request notes:

- `diagnostic/build-<commit-4-bytes>.logd`
- `diagnostic/build-<commit-4-bytes>.json`, when present

Commit the diagnostic files only when the issue or PR template requires
them. Do not commit ordinary build products such as binaries, `node_modules`,
`target/`, or local caches.

## Coding Conventions

- Keep changes scoped to the issue. Avoid drive-by cleanup.
- Read the nearest module before editing. This repo rewards imitation more
  than invention.
- Prefer explicit configuration over hidden defaults.
- Preserve the existing language and error-handling style in each module.
- Add comments only when they prevent future archaeology.
- Do not hardcode secrets, tokens, personal data, or local paths.
- Update docs when commands, config, or behavior changes.
- Use deterministic filenames for generated project helpers when possible.

## Known Pitfalls

- `build.py` builds every module by default. Missing system dependencies can
  fail unrelated modules, but it should still produce diagnostics.
- Diagnostic filenames are based on the current commit hash, so they change
  after a new commit.
- The `encryptly` helper is required for real `.logd` output.
- Several modules have intentionally blunt comments. Match the practical,
  self-aware tone, but do not turn every comment into a performance.
- The market module contains many analytics types. Check existing names
  before adding new metrics or labels.
- The PR template requires local testing notes and diagnostic build evidence.

## Hermes Session Instructions

- Start from the issue text and identify the affected module first.
- Before editing, read the files listed in "Where to Start" for that module.
- After editing, run `python3 build.py`.
- Put the diagnostic `.logd` path, and matching `.json` path if present, in
  the PR body.
- Use `.github/pull_request_template.md` exactly. It exists for a reason,
  which is more than can be said for some of the legacy build assumptions.
